# Git

Правила работы с ветками, коммитами и push для Юлии: она решает, что и когда уходит в origin, я слежу за свежестью ветки и чистотой истории.

## Ветка

- Названный тикет (ключ или ссылка) = новая ветка под него. Не продолжать ту, что сейчас выбрана, даже если работа уже идёт на ней.
- Порядок: проверить текущую ветку → `git fetch origin` → подтвердить правильную базу → создать ветку `feature/<описательное-имя>` от свежей базы. Всё это до первой строки дизайн-дока или кода.
- База — базовая ветка проекта по его конвенции (таблица веток в правилах репозитория), а не `main` / `dev` по привычке.

## Свежесть ветки

- Следить за origin самой, не ждать напоминания. Чекпоинты: старт сессии, после каждой задачи SDD, перед каждым прогоном или гейтом, перед запуском ревью-цикла, перед финальной проверкой, перед открытием MR, перед словом «готово», после долгого фонового ожидания.
- На чекпоинте: `git fetch origin`, затем `git log --oneline HEAD..origin/<база>`. Непустой вывод = сначала доложить, что приехало, затем подлить базу мёржем и перегнать затронутые проверки на результате слияния.
- Проверять не только базу: сравнивать свою ветку с её копией на origin, туда попадают правки ревью из других сессий. Приехало — доложить, подлить мёржем, перепроверить.
- Стековая ветка (отрезана от другой фичи): ревью только своих коммитов; базовую ветку проекта не проверять и не подливать. Родительскую фичу, от которой отрезана ветка, подливать по общим правилам: она тоже уезжает, и дольше всего болит именно это.
- Мёрж, не ребейз. Подливать базу мёрж-коммитом сверху: старые SHA не меняются, force-push не нужен.
- Ребейз только по её явному слову в этот день для этой ветки. Локальная незапушенная ветка не исключение. Ситуация необычная — спросить, что она хочет, а не решать.

## Стейджинг и коммиты

- Никогда `git add -A` / `git add .`. Только именованные пути. Правка затронула много файлов — взять список из `git status` и стейджить каждый явно.
- Перед каждым коммитом читать staged: `git diff --cached --name-only`. Путь, который я не писала специально для этого изменения, в коммит не идёт.
- Неотслеживаемое и не игнорируемое — опасное состояние. Инструмент или агент оставляет артефакты прогона в рабочем дереве — тем же коммитом добавить правило в ignore. Пробные тесты и отчёты агентов в ветку не попадают.
- Формат коммитов проекта соблюдать буквально. Обычно: `[action](TICKET): summary`, затем по строке на файл: что изменено и зачем.
- Никакого трейлера `Co-Authored-By` от любой модели. Хук или шаблон добавил — убрать до коммита.
- Файлы планов коммитить один раз, при создании. Дальнейшие правки плана отдельным коммитом не оформлять: они уезжают вместе со следующим коммитом кода или спеки. Спеки, наоборот, получают свои коммиты.

## Правки по ревью и ротация MR

- Правка по ревью на незапушенный коммит — amend с целостным сообщением. На запушенный — новый коммит. Force-push запрещён.
- Вернувшийся с замечаниями MR: починить → прогнать проверки → закоммитить → запушить (по её команде) → ответить комментарием в MR по пунктам ревьюера, отклонённое назвать с причиной → обновить описание MR.

## Push

- Push только по отдельной явной команде «запушь». Новая ветка — тоже push. «Да, давай» на составной вопрос, где push один из пунктов, согласием на push не считается.
- Push всегда отдельный вопрос или шаг. По умолчанию коммиты остаются локальными.
- Слово «пуш» в моих сообщениях появляется только после всех проверочных прогонов и чистого раунда ревью.
- Перед каждым push, первым и любым следующим, а не только перед созданием MR: `git fetch origin <база>`, затем настоящая проверка слияния `git merge-tree --write-tree HEAD origin/<база>`. Старая трёхаргументная форма `merge-tree` содержательные конфликты не ловит, ей не пользоваться.
- Для открытого MR дополнительно `gh pr view --json mergeable,mergeStateStatus`.
- Конфликт = сначала доклад, решает она. Разрешение только мёржем базы в ветку и только по её команде.

## Разбор коммитов

- Разбор идёт по одному коммиту. После каждого ждать «дальше», не выкладывать все сразу.
- Структура одного коммита, в этом порядке:
  1. ID и заголовок дословно из `git log`, отдельной строкой, без русского пересказа в той же строке.
  2. Одна фраза сути бытовыми словами.
  3. По каждому файлу: реальный кусок диффа из `git show <hash> -- <file>`, затем 2–3 фразы «было / стало» на конкретном примере запроса или входа. Сначала пример, потом техническая деталь. Отдельно «зачем», привязанное к тому же примеру.
  4. Тесты одной строкой: что проверяют и какой баг вернулся бы без них.
- Каждый раздел 1–2 фразы, без оговорок и «дополнительно». Нюансы файла только по её уточняющему вопросу.
- Дифф обязателен: сжатая проза без реального куска файла выглядит расплывчато и не принимается.

## «Посмотри PR»

- «Посмотри PR» / «сделай ревью PR» / «запусти ревью на PR» = только отчёт о находках. Никаких локальных правок, коммитов и патчей.
- Ревью-workflow на PR запускать с явным `fix:false`: по умолчанию он чинит.
- Результат — таблица реальных проблем: файл, суть, серьёзность. Что чинить и кто чинит, решает она.
- Чинить только по отдельной явной команде и через SDD.
