# Спека → план → код

Любое нетривиальное изменение (включая инфраструктуру и terraform) идёт по одному конвейеру, и на каждой границе Юлия даёт отдельную отмашку.

## Порядок шагов

- Порядок всегда: брейншторм → спека → план → код. Спеку и план она валидирует до того, как тронут код.
- Полный конвейер: superpowers:brainstorming → /clarifying → superpowers:writing-plans → /analyzing → superpowers:subagent-driven-development (superpowers:executing-plans, если она сказала выполнять план в отдельной сессии) → /converging, повторять до статуса Converged → superpowers:verification-before-completion → ревью кода → superpowers:finishing-a-development-branch.
- /clarifying запускать после того, как брейншторм записал спеку, и до плана: он задаёт до пяти вопросов, включая решения, которые модель приняла без неё, и вписывает ответы в спеку.
- /analyzing запускать после плана и до исполнения: только чтение, сверка спеки и плана между собой.
- /converging запускать после исполнения плана: сверка кода со спекой и планом, недостающие задачи дописывать в конец плана под заголовком `## Convergence N`, только добавлением, существующие задачи не трогать.
- Скиллы /clarifying, /analyzing, /converging лежат в `~/.claude/skills/<имя>/SKILL.md`. Их текст держать близко к оригиналам spec-kit (clarify.md, analyze.md), не переписывать вольно.
- Глобальные правила для всех проектов лежат в `~/.claude/constitution.md` в формате MUST / NEVER по шаблону spec-kit. Заполнять его вместе с ней, сохраняя структуру шаблона. Проектный CLAUDE.md читать как дополнение с той же силой.
- Скиллы вызывать реально через Skill, а не воспроизводить их процесс по памяти. «Запусти субагентов» / «через субагентов» = Skill(superpowers:subagent-driven-development) с путём к плану в args и весь его процесс: рабочее пространство, журнал, брифы исполнителям, ревью на каждую задачу, раунды починок. «Запусти дебаг» = superpowers:systematic-debugging. «Напиши спеку» = superpowers:brainstorming, затем superpowers:writing-plans.
- Перед началом любой фичи спросить у неё исходные данные для базового прогона и дождаться их, если проект такой прогон предполагает.
- Если конвенция проекта требует плагин или инструмент, которого нет в сессии, сказать это сразу, а не описывать обходной путь как равноценный.

## Отмашки

- Ни одного файла не создавать и не править, пока она явно не сказала «пиши» / «да». До этого объяснить, как вещь будет работать: коротко, по-русски, с текстовой ASCII-схемой в блоке кода.
- Порядок перед записью: показать устройство → задать оставшиеся вопросы по одному на сообщение → свести принятые решения в один список → дождаться «пиши» → только тогда писать.
- «Делай» по идее означает согласие с идеей, а не разрешение писать код и не разрешение коммитить.
- Одобренная спека = разрешение писать план. Одобренный план ≠ разрешение начинать реализацию: старт только после её отдельной отмашки.
- Не заканчивать ответ предложением «начать писать код» или «реализовать сейчас», даже если у задачи уже известны причина и номера строк. План заканчивается планом, разбор заканчивается разбором.
- Не коммитить без её явной команды, даже после того, как она согласилась, что изменение нужно. Показать дифф «перед пушем» не заменяет её контрольную точку на спеке и плане.
- Никаких изменений в `src/`, в промптах и в любых рабочих файлах до отмашки, даже «временных, чтобы прогнать тесты» с планом сразу откатить. Для проверки кандидата в изменение делать копию модуля в scratchpad и подключать её из скрипта (sys.path или monkeypatch), либо просто показать разбор и ждать.
- Найденный баг, в том числе вызванный моей же правкой и посреди срочного потока, не разрешает правку. Диагноз и предлагаемый дифф показать текстом и ждать её отмашку на каждую починку отдельно.
- Находки ревью не чинить сразу после разбора: таблица «что предлагаю чинить», вопросы кнопками, стоп. Чинить только после явного «погнали», через superpowers:subagent-driven-development.

## Брейншторм и вопросы

- Брейншторм только через скилл superpowers:brainstorming, объявить это вслух. Не собирать брейншторм из своих Agent-вызовов и промптов.
- Одна фича = один вызов скилла, одна спека, один план. Две фичи = два отдельных вызова, две спеки, два плана, не сливать.
- Каждый вопрос через AskUserQuestion кнопками, по одному вопросу за ход. Моя рекомендация первой, с пометкой (Recommended) и причиной в описании; у каждого варианта одна строка последствий. Нейтральный список без позиции не годится.
- Вопрос прозой «A или B?» в чате запрещён, включая вопросы во время брейншторма и до записи файла.
- «Сама обоснуй» = ответить в чате с ASCII-схемой, затем перейти к следующему вопросу кнопками.
- Настройки и длинные конфигурационные опросы наоборот: не водить по двадцати вопросам. Выставить разумные значения по умолчанию, показать сводку и спросить одним «ок или поправить X». Спрашивать только там, где решение действительно за ней.

## Код правят субагенты

- Инлайн-правки кода моими Edit / Write в основной сессии запрещены без явного разрешения именно на инлайн именно в этой задаче. Реализация идёт через субагентов: superpowers:subagent-driven-development, Agent-вызовы или workflow, что уместно.
- Размер правки роли не играет: «маленький фикс» тоже делает субагент.
- Отмашка на старт задачи не равна разрешению на инлайн. Разрешение на инлайн не переносится между задачами и сессиями.
- Перед первым Edit / Write по коду проверить: было ли явное разрешение на инлайн в этой задаче. Нет — поднять субагента на правку.
- Финальное ревью всей ветки в конце superpowers:subagent-driven-development не запускать: его она запускает сама.

## Спека и план как файлы

- Спеки лежат в `docs/superpowers/specs/`, планы в `docs/superpowers/plans/`.
- Спеки писать по-английски. Jira (заголовок и описание) по-английски. Чат при этом остаётся русским.
- Язык планов не зафиксирован: спросить у неё или посмотреть язык последнего плана в репозитории, не предполагать.
- Код, промпты, ссылки вида файл:строка, имена полей остаются на английском при любом языке окружающего текста.
- Спека получает свой коммит: это долговременная запись (дизайн, разбор причины бага).
- План коммитить только один раз, при создании. Дальнейшие правки плана (новый шаг, порядок, исправление после ревью) отдельными коммитами не оформлять: править на диске свободно, а в git они попадают вместе со следующим настоящим коммитом кода или спеки.
- «Открой спеку» / «дай план» / «где ссылка на спеку» = открыть файл в VS Code бинарником по абсолютному пути (командой `code <абсолютный путь>` (бинарник VS Code по абсолютному пути, найти на текущей машине)) и написать в чат абсолютный путь. Относительный путь не подходит: его не открыть кликом.
- Не пересказывать документ в чат и не отправлять его карточкой файла: до неё такое не доходит. Только открыть и дать путь.
- Если файл есть только на другой ветке, сначала вытащить его через `git show <ветка>:<путь> > <файл>`, затем открыть.
- Когда брейншторм закончил спеку, сразу открыть её в VS Code и дать абсолютный путь.
